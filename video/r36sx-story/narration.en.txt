A handheld with another life
This little handheld was sold as a ready-made game console. I wanted to know what else it could become. Behind the stock menu, I found a Linux system, a MIPS processor, and a software stack worth exploring. The journey led from a moving square on the screen to my own launcher, native applications, and DOS software running on the actual device. This is how I got there.

Start with the evidence
The first problem arrived before any code ran. The card supplied with the console was labelled sixty-four gigabytes, but its real capacity was sixteen. Its partition table was damaged, and Windows wanted to format it. TestDisk recovered the partition table. A raw backup gave me a reference to preserve, and copies of that image became the starting point for experiments. Even the storage needed to be understood before the firmware could be trusted.

Look past the filenames
The files on the card held the next surprise. A file named advapi thirty-two dot D L L was actually a Linux boot image. Another D L L contained the A V P firmware, while a screensaver-looking filename concealed a device tree. The executable files identified the main userspace as little-endian MIPS. The same processor architecture is also used in many home routers. The saved system report showed only about forty-two mebibytes of usable RAM, a very small budget for the software I wanted to run. I used Ghidra and the extracted filesystem to map the launcher, helper programs, and hardware library. Their names were clues to investigate, not reliable descriptions of their contents.

Find the software boundary
The stock frontend, called r k game, loaded emulator cores from shared libraries. Those cores exposed a familiar libretro-style interface, with extra compatibility symbols expected by the vendor. That gave me a practical entry point. I could keep the kernel and hardware support in place while adding my own userspace code. The extension mappings and per-file overrides showed how to route a test file to a custom core. A small experiment could answer a much bigger question: could this console run my software?

The first visible proof
My first useful proof was deliberately simple: a square, a framebuffer, and a log of button presses. Getting even that onto the screen took several revisions. I matched the stock core interface, removed unwanted runtime dependencies, and used a normal Game Boy filename with an explicit core override. Then I tested the controls, colours, resolution, and sound. The square was modest, but it proved that code I built could be selected in the stock menu and interact with the real handheld.

Reuse the path that already works
Next, I wanted a launcher for native programs. The first Tiny M C experiments exposed an important detail: drawing pixels was only part of the display path. The stock frontend relied on driver dot S O for video and input. I studied that library and reused its frame presentation and control functions. Tiny M C became a small, button-driven file manager with readable text, directory navigation, and direct program launching. The reverse engineering was turning into infrastructure I could build on.

Let a boot log settle the question
One of the most useful discoveries came from a failed assumption. A script named i cube start looked like the obvious place to change startup behaviour. But changing it did not control the cold boot I was observing. I added temporary tracing and captured the actual path on the device. The log showed i cube dot S H starting the stock supervisor and frontend. Redirecting that script made Tiny M C start at boot. The name suggested a route; the live trace established which route this device really used.

Turn experiments into applications
With a launcher and working hardware access, native applications became easier to test. Pong reused the same core game logic in both a launcher-loaded module and a standalone program. Shared helpers covered hardware constants, fonts, audio, and later screenshots. There were still practical failures to solve: returning from an application could leave a black screen, and button presses could leak across menus. Fixing those transitions mattered just as much as getting the first successful frame.

A different machine inside the handheld
The next step was a personal computer emulator. I ported the existing open-source Pico-286 project to this Linux handheld, replacing the host integration with the console's display, controls, and audio path. The repository records a successful DOS boot on May twenty-eighth. Soon the result was more than a boot message: FreeDOS appeared on the console, and Volkov Commander could browse files inside the emulated P C. An upstream emulator had become a native application on a very different machine.

Make a PC usable with game controls
Booting DOS was a milestone, but a P C expects more keys than a handheld provides. I added an on-screen keyboard, remappable button presets, and menus for binding floppy and hard-disk images. Function-button combinations opened those tools without taking away the main controls. Preset editing, disk activity feedback, and screenshot shortcuts made the port more useful away from the development computer. These were small interface details with a direct effect on what software I could actually use.

A running program is only the beginning
Real DOS programs exposed the next layer of problems. A screen could look almost right while its palette, memory layout, or scrolling was still wrong. The work expanded into C G A, E G A, and V G A rendering, along with timing, disk caching, and frame presentation. Preserved captures show Supaplex and the SuperScape benchmark running in the port. Profiling and diagnostics helped separate visible results from the bugs behind them. Getting software to launch was the beginning of compatibility work, rather than the end.

Keep checking the machine being emulated
The later repository history goes beyond what these early videos show. Work continued on the 80386 path, protected-mode behaviour, video conformance, and targeted regression probes. A Windows debug build made it possible to investigate the same emulator sources without copying every experiment to the console. Tests covered details such as division faults, stack updates, and repeated string operations. This part of the story is documented by code and test records. It is ongoing engineering, and individual host-side checks should not be mistaken for complete compatibility on hardware.

Keep the next step separate from the result
The investigation also produced a native shell frontend. Through the USB O T G port, I managed to connect a physical keyboard and a USB flash drive. I also built tools for exploring an alternative Debian userspace from an S D card. That opened another line of research into the boot chain and device tree. I kept those experiments distinct from the working application demonstrations. Preserving the stock hardware support and keeping recoverable card images made it possible to explore further without treating a plan, a built image, and a verified device boot as the same achievement.

From a closed menu to an open experiment
Looking back, the important progress came from a repeatable loop: inspect the existing system, form a small hypothesis, build a test, and check it on the device. Ghidra analysis, hardware traces, open-source projects, and A I assisted coding all played a part. The result is a documented route from the stock firmware to custom native software and a usable DOS port. There is more to improve, but this little console has already become a much more interesting machine to work with.
