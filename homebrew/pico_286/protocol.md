# HOSTRPC Stream Protocol

Этот документ описывает вызов процедур хоста из гостевой DOS-программы.
Обмен идет через один двунаправленный 16-битный stream port. Инициатором всегда
выступает гостевая программа: она отправляет команду или данные через `OUT DX, AX`,
а затем ожидает ответ хоста по изменению бита синхронизации.

Обратной совместимости с 8-битным HOSTRPC transport больше нет. Byte `IN/OUT`
к `E360h` не являются частью RPC-протокола.

## Порты

| Назначение | Значение |
| --- | --- |
| HOSTRPC stream data/command port | `E360h` |
| Диагностический HOSTDRV trace port | `E36Ah` |
| Emergency dump port | `E36Bh` |

Гостевые DOS-утилиты используют определения из
`homebrew/pico_286/pico-286/tools/hostrpc.inc`. Хостовая реализация живет в
`homebrew/pico_286/r36sx_port/r36sx_host_rpc.c.inl`; номера команд в этих
файлах должны оставаться синхронизированными.

Других HOSTRPC command/address/result портов нет. Команда, адрес request block
и ответные коды передаются через основной stream port `E360h`. Диагностический
trace port и emergency dump port не являются частью RPC-протокола данных.

## Формат Кадра

Каждая запись в stream port имеет 16 бит:

| Бит 15 | Биты 14..0 | Значение |
| --- | --- | --- |
| `1` | command id | Командный кадр |
| `0` | data payload | Кадр данных с 15 полезными битами |

Константы:

| Имя | Значение |
| --- | --- |
| `PROTO_CMD_FLAG` | `8000h` |
| `PROTO_DATA_MASK` | `7FFFh` |
| `PROTO_ERR_TOO_LARGE` | `7FFDh` |
| `PROTO_ERR_MISMATCH` | `7FFEh` |
| `PROTO_ERR` | `7FFFh` |

Командный кадр отправляется как `8000h | command_id`. Кадр данных отправляется
как `payload & 7FFFh`.

## Синхронизация

Перед началом обмена гостевая программа читает `E360h` через `IN AX, DX` и
сохраняет текущий бит 15. После каждой записи в порт гость циклически читает
`E360h`, пока бит 15 не изменится. Изменение бита означает, что хост принял
кадр и записал ответ.

Нижние 15 бит ответа содержат код результата или часть данных. Если хост не
ответил за заданный таймаут, например за 5 секунд, гостевая программа должна
завершить операцию с ошибкой "host unavailable".

## Начало Сеанса

Обычная последовательность инициализации:

1. Прочитать `E360h` через `IN AX, DX` и сохранить текущий sync bit.
2. Отправить `RESET` (`8000h | 0`).
3. Дождаться ответа. В текущей реализации хост возвращает версию протокола.
4. Отправить `PING` (`8000h | 1`).
5. Дождаться ответа и проверить, что нижние 15 бит равны `RPC_VERSION`.

Текущая версия stream/request-block ABI: `5`.

## Управляющие Команды

| Команда | ID | Ответ |
| --- | --- | --- |
| `RESET` | `0` | Сбрасывает stream state, закрывает host handles, возвращает версию |
| `PING` | `1` | Возвращает версию |
| `CONTINUE` | `2` | Зарезервировано для многофреймовых ответов |
| `ABORT` | `3` | Прерывает текущую передачу, возвращает `0` |
| `END` | `4` | Завершает текущую передачу, возвращает `0` |

ID `5..9` зарезервированы для обслуживания протокола. Дополнительной команды
`CALL` нет: гость вызывает команды хоста напрямую через command id.

## Команды Хоста

Команды хоста используют то же поле command id и начинаются с `10`, чтобы
первые десять значений `0..9` оставались служебным диапазоном протокола. После
командного кадра гость передает физический адрес request block ровно тремя
15-битными data frames. Операция выбирается command id из командного кадра;
поле `command` внутри request block остается зеркалом для отладки и подготовки
запроса.

| Команда | ID | Назначение |
| --- | --- | --- |
| `CMD_OPEN_RO` | `10` | Открыть файл только для чтения |
| `CMD_OPEN_RW` | `11` | Открыть файл для чтения и записи |
| `CMD_CREATE` | `12` | Создать или обрезать файл |
| `CMD_CLOSE` | `13` | Закрыть file handle |
| `CMD_READ` | `14` | Прочитать данные в гостевую память |
| `CMD_WRITE` | `15` | Записать данные из гостевой памяти |
| `CMD_DELETE` | `16` | Удалить файл |
| `CMD_MKDIR` | `17` | Создать каталог |
| `CMD_RMDIR` | `18` | Удалить каталог |
| `CMD_GETATTR` | `19` | Получить атрибуты, размер и дату/время |
| `CMD_RENAME` | `20` | Переименовать файл или каталог |
| `CMD_COMMIT` | `21` | Сбросить буферы открытого файла |
| `CMD_FIND_FIRST` | `22` | Начать поиск по маске |
| `CMD_FIND_NEXT` | `23` | Продолжить поиск |
| `CMD_FIND_CLOSE` | `24` | Закрыть search handle |
| `CMD_CLOSE_ALL` | `25` | Закрыть все handles текущего redirector instance |
| `CMD_CHDIR` | `26` | Проверить и запомнить текущий каталог mapped drive |

## Адрес Request Block

Физический адрес request block передается младшими битами вперед как три
15-битных data frames:

| Кадр | Биты адреса | Payload |
| --- | --- | --- |
| `0` | `0..14` | `addr & 7FFFh` |
| `1` | `15..29` | `(addr >> 15) & 7FFFh` |
| `2` | `30..31` | `(addr >> 30) & 0003h` |

После первых двух data frames хост переключает sync bit и возвращает `0`.
После третьего кадра хост выполняет команду, записывает результат обратно в
request block и возвращает `REQ_RESULT` в нижних 15 битах. Если запрос не
принят или команда завершилась нештатно на уровне транспорта, возвращается
один из зарезервированных transport error codes.

Адресная посылка для файловых команд имеет фиксированный размер: ровно три
data frames. Если до третьего data frame приходит новая команда, `END`,
`CONTINUE` или `PING`, хост отвечает `7FFEh` (`PROTO_ERR_MISMATCH`) и
сбрасывает текущую передачу как несовпадение состояния протокола. `RESET` и
`ABORT` остаются командами аварийной ресинхронизации. Если data frame приходит
сразу после уже принятой 3-кадровой посылки, хост отвечает `7FFDh`
(`PROTO_ERR_TOO_LARGE`). Если третий address frame содержит биты выше `31`,
хост также отвечает `7FFDh`. Data frame без активной файловой команды и без
предыдущей fixed-size посылки считается protocol mismatch и возвращает
`7FFEh`.

## Request Block

Все поля little-endian и лежат в гостевой физической памяти.

| Offset | Поле | Размер | Описание |
| --- | --- | --- | --- |
| `0` | `magic` | `word` | `5248h`, ASCII `"HR"` в little-endian |
| `2` | `version` | `word` | Версия ABI, сейчас `5` |
| `4` | `command` | `word` | Зеркало command id для отладки/подготовки |
| `6` | `flags` | `word` | Флаги запроса |
| `8` | `path_phys` | `dword` | Физический адрес первого ASCIIZ пути |
| `12` | `path2_phys` | `dword` | Физический адрес второго ASCIIZ пути |
| `16` | `data_phys` | `dword` | Физический адрес буфера данных |
| `20` | `data_len` | `dword` | Размер буфера или запрошенной передачи |
| `24` | `file_pos` | `dword` | Позиция в файле |
| `28` | `file_size` | `dword` | Размер файла или новое значение размера |
| `32` | `handle` | `word` | File/search handle |
| `34` | `mode` | `word` | DOS/access mode |
| `36` | `attr` | `word` | DOS attributes |
| `38` | `dos_error` | `word` | DOS-compatible error code |
| `40` | `result` | `word` | HOSTRPC result code |
| `42` | `reserved` | `word` | Для metadata: packed DOS time |
| `44` | `bytes_done` | `dword` | Количество байт; младшее word также packed DOS date |
| `48` | Конец | | Размер структуры |

`REQ_FLAG_CREATE_NEW` (`0001h`) просит `CMD_CREATE` вернуть ошибку, если файл
уже существует.

## Результаты

Основной результат операции записывается в `result` и дублируется в 15-битном
ответе на последний address frame, если значение помещается в обычный диапазон
result codes. Значения `7FFDh..7FFFh` зарезервированы для transport errors:

| Код | Имя | Значение |
| --- | --- | --- |
| `7FFDh` | `PROTO_ERR_TOO_LARGE` | Fixed-size request получил лишний data frame |
| `7FFEh` | `PROTO_ERR_MISMATCH` | Состояние гостя и хоста разошлось |
| `7FFFh` | `PROTO_ERR` | Общая ошибка протокола |

Текущие host-side result codes:

| Код | Значение |
| --- | --- |
| `0` | OK |
| `1` | Bad request |
| `2` | Bad guest memory address |
| `3` | Bad path |
| `4` | No free handle |
| `5` | Bad handle |
| `6` | Host I/O error |

DOS-совместимая причина ошибки, если она есть, возвращается отдельно в
`dos_error`.

## Многофреймовые Ответы

Исходная схема протокола допускает ответы длиннее 15 бит: хост может вернуть
первый 15-битный фрагмент сразу, а гость затем запрашивает следующие фрагменты
командой `CONTINUE`.

Для ответа фиксированного размера значение разбивается на 15-битные куски,
начиная с младших битов. Для ответа переменного размера первый ответ может
содержать длину в байтах, после чего гость получает данные через `CONTINUE`.

Текущие файловые HOSTRPC команды используют request block вместо stream
ответов переменной длины, поэтому `CONTINUE` пока зарезервирован и отвечает
`0`.

## Передача Данных От Гостя

Для простых stream-команд данные могут следовать после командного кадра как
data frames с очищенным битом 15. Хост обязан переключать sync bit после
каждого принятого кадра.

Файловые HOSTRPC команды передают через stream только физический адрес request
block. Собственные payload-данные файловых операций лежат в гостевой памяти по
`data_phys`, а их размер задается `data_len`.

## Пример PING

```text
Guest                                              Host
-----                                              ----
IN  AX, DX       ; DX = E360h, сохранить sync bit 15
OUT DX, AX       ; AX = 8000h | PING
poll E360h       ; ждать смены sync bit 15
IN  AX, DX       ; low 15 bits == RPC_VERSION
```

## Пример Файловой Команды

```text
Guest                                              Host
-----                                              ----
Заполнить request block
OUT E360h, 8000h | CMD_READ
poll E360h       ; ACK
OUT E360h, addr bits 0..14
poll E360h       ; ACK
OUT E360h, addr bits 15..29
poll E360h       ; ACK
OUT E360h, addr bits 30..31
poll E360h       ; команда выполнена
Прочитать обновленный request block
```
