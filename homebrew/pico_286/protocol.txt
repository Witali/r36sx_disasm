Этот протокол описывает вызов процедур хоста из гостевой программы.
Обмен идет через один двунаправленный 16-битный порт E360h. Инициатором обмена
выступает гостевая программа. Обратной совместимости с 8-битным transport нет:
гость должен использовать OUT DX, AX и IN AX, DX.

При отправке запроса хост может отследить появление новых данных в порту по
записи гостя. Гостевая программа ждет ответ по изменению бита синхронизации.
То есть перед отправкой сообщения хосту гостевая программа должна прочитать и
сохранить значение порта обмена, отправить свое сообщение хосту, и после этого
проверять изменение бита синхронизации. Если после определенного времени,
скажем 5 секунд, от хоста не пришел ответ, то гостевая программа завершает
операцию с сообщением "Хост недоступен".

Бит синхронизации - наиболее значащий бит 16-битного слова, то есть bit 15.

Каждый кадр имеет 16 бит:

bit 15 = 1: команда протокола или команда хоста.
bits 14..0: command id.

bit 15 = 0: данные.
bits 14..0: 15 бит полезных данных.

Основные константы:

PROTO_CMD_FLAG  = 8000h
PROTO_DATA_MASK = 7FFFh
PROTO_ERR_TOO_LARGE = 7FFDh
PROTO_ERR_MISMATCH  = 7FFEh
PROTO_ERR           = 7FFFh

Пример протокола: команда PING, определение доступности хоста.

Гостевая программа                                        Хост
|                                                            |
| <-  IN AX, DX для сохранения bit 15 синхронизации -------- |
|   (не нужно если бит уже сохранен от предыдущего обмена)   |
|                                                            |
| - OUT DX, AX: AX = 8000h | PING                         -> |
|                                                            |
| <- <- <- Циклическое чтение до изменения bit 15            |
| <- Бит изменился, lower 15 bits содержат RPC_VERSION ----- |

Если функции RPC достаточно 15 бит для ответа, она сразу возвращает его в
нижних 15 битах.

Если функция возвращает ответ фиксированного размера, то разбивает его на
куски по 15 бит. Гостевая программа может запросить продолжение командой
CONTINUE. Текущие файловые команды используют request block в памяти гостя,
поэтому многофреймовые stream-ответы пока зарезервированы.

Передача данных от гостевой программы хосту выглядит похоже: после отправки
команды в порт гостевая программа отправляет data frames с нулевым старшим
битом. На каждый отправленный word хост отвечает изменением бита синхронизации.

Файловые команды хоста начинаются с command id 10. Первые 10 команд, 0..9,
зарезервированы для обслуживания протокола. Дополнительной команды CALL нет:
гость вызывает команды хоста напрямую.

Для файловой команды гость после command frame отправляет физический адрес
request block ровно тремя data frames:

frame 0: bits 0..14  = addr & 7FFFh
frame 1: bits 15..29 = (addr >> 15) & 7FFFh
frame 2: bits 30..31 = (addr >> 30) & 0003h

Если гость отправляет команду раньше, чем хост получил все три address frames,
хост возвращает PROTO_ERR_MISMATCH. Если после фиксированной трехкадровой
посылки приходит лишний data frame, или третий address frame содержит биты
выше 31, хост возвращает PROTO_ERR_TOO_LARGE.

Кроме вызываемых функций, необходимы функции управления потоком: RESET, PING,
CONTINUE, ABORT и END. RESET полностью сбрасывает состояние хоста в начале
сессии обмена. PING возвращает текущую версию протокола. ABORT прерывает
текущую команду. END сигнализирует окончание передачи.

Текущая версия stream/request-block ABI: 5.

Команды протокола описаны в hostrpc.inc и r36sx_host_rpc.c.inl. Эти файлы
должны оставаться синхронизированными для хоста и гостевой программы.
