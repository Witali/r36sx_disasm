# Свой Linux и лёгкая оболочка на R36SX

Исследование: 18 октября 2026 года. Проверены локальные образы, дамп загрузчика,
сохранённые сведения с устройства, исходники HCRTOS и актуальные материалы
проекта r36sx-hclinux. В этой работе устройство не перепрошивалось и новое
ядро на нём не запускалось.

Дополнение: в загрузчике найдена функция чтения **общего объёма DDR из
контроллера**, независимо от Linux. Подготовлена SD-утилита
`patches/disk_image_patch_physical_memory_probe/`; аппаратный запуск пока
ожидается. См. `disasm/mips/r36sx-linux-boot/DDR_READOUT.md`. В метаданных
DDR-init записано 256 МиБ, но это параметры образа инициализации, а не
измерение установленной RAM. Вывод о 128 МиБ по меньшей карте памяти ниже
остаётся гипотезой до прямой проверки.

## Вывод

**Да: свою оболочку можно запускать на штатном Linux; своё ядро тоже реально
собрать, если сохранить поддержку Hichip HC16xx и согласованную карту памяти.**
Практичный первый вариант — небольшая система Buildroot/BusyBox и графическое
меню или файловый менеджер через существующий видеостек. Замена ядра для этого
не обязательна. Полноценный рабочий стол с X11 требует отдельного запуска
графики и ввода; его пригодность на этой консоли пока не проверена.

Это MIPS 74Kc, MIPS32r2 little-endian, пользовательский ABI O32. Основа уже
содержит Linux 4.4.186 и Buildroot. Hichip-специфичные драйверы и AVP/HCRTOS
обслуживают мультимедиа; обычного ядра «для MIPS вообще» недостаточно.

## Главное новое: два комплекта загрузочных файлов

Свежая декомпиляция `FUN_89da926c` и дизассемблирование `0x89daa730` показывают,
что загрузчик проверяет зеркалирование памяти на расстоянии 128 МиБ. Результат
управляет таблицей переименования файлов:

| Запрошенный файл | При обнаружении зеркалирования памяти |
| --- | --- |
| `vmlinux.uImage` | `advapi32.dll` |
| `dtb.bin` | `Bubbles.scr` |
| `avp.uImage` | `ApplicationFrame.dll` |

Файлы `.dll` — настоящие образы Linux/AVP в контейнере uImage, а `.scr` — DTB.
Выбор выполняется внутри загрузчика, поэтому изменить только
`cubegm/vmlinux.uImage` может оказаться недостаточно для конкретной консоли.

Независимый разбор образов дал:

| Показатель | Обычные имена | Замаскированные имена |
| --- | --- | --- |
| Ядро | 4.4.186-release **#7** | 4.4.186-release **#21** |
| Linux load / entry | `0x80000000` / `0x803337c0` | те же |
| AVP load / entry | `0x8bda4000` | `0x83da4000` |
| Регион Linux в DTB | 175,57 МиБ | 47,57 МиБ |

Сохранённый `hardware_info/mtd-dump/uname.txt` содержит **#21**, а
`hardware_info/mem.txt` — `MemTotal: 43164 kB`, то есть 42,15 МиБ. Эти два факта
согласуются с меньшим комплектом и предположением о 128 МиБ физической RAM,
значительная часть которой отведена AVP/мультимедиа. Это сильная интерпретация
сохранённых данных, но текущая физическая конфигурация заново не измерялась.

Нельзя обещать 176 МиБ Linux RAM, основываясь только на наличии `dtb.bin` на
карте. Нельзя получить дополнительную физическую память, просто заменив DTB.

Техническая оговорка: Ghidra ошибочно убрала условную ветку RAM-пробы как
недостижимую. Вывод выше основан на проверенных инструкциях, где сравнение и
запись переключателя присутствуют, а не на этой ошибке псевдокода.

## Что получилось восстановить

В Ghidra заново разобраны девять функций Stage 3: поиск файла, выбор ресурса,
чтение uImage, запуск `bootm`, проверка CRC заголовка/данных и передача
управления ядру. Последняя использует адрес из заголовка и аргументы
`(-2, dtb, 0, 0)`. В исследованном пути обнаружены проверки CRC/архитектуры;
криптографическая подпись ядра в этом пути не выявлена. Это не полный аудит
BootROM и всех механизмов обновления прошивки.

Из обоих ядер распакован встроенный initramfs. В каждом основной архив содержит
380 записей, а стартовые скрипты совпадают. Установлена цепочка:

```text
Stage 3 -> выбранные DTB + AVP + Linux с SD
Linux -> встроенный /init -> BusyBox init -> rcS
  -> S10mdev
  -> S41hcdaemon
  -> S99app -> /mnt/sdcard/cubegm/icube.sh -> оболочка
```

`S99app` сам ждёт файл `cubegm/icube`, подключает каталог `rootfs` с карты и
вызывает `icube.sh`. При небольшой памяти он также включает 128 МиБ swap.
Следовательно, для первого своего интерфейса достаточно использовать уже
освоенный запуск через `icube.sh`; файл-сигнал `cubegm/icube` пока надо
сохранить. Наличие swap не превращает его в быструю оперативную память.

`disk_image/rootfs/linuxrc` совпадает с BusyBox побайтно; внутри initramfs
`linuxrc` — ссылка на BusyBox. Декомпилировать его целиком для понимания запуска
не потребовалось: настоящая логика находится в извлечённых скриптах.

Для графики изучены существующие результаты декомпиляции `driver.so`:
`disasm/disk_image/mips_elf/driver/`. Она работает с `/dev/dis`, `/dev/fb0`,
`/dev/ge`, аудио и общей памятью кнопок. Начальный интерфейс разумно строить на
уже работающем коде `homebrew/tiny_mc`, `homebrew/shell` и `homebrew/common`.
Переход на стандартные ALSA/DRM/evdev нельзя считать автоматически готовым.

## Более свежий проект со своим ядром

[r36sx-hclinux](https://github.com/ozkaoz/r36sx-hclinux) содержит сборочную
обвязку, изменения для ядра и документацию собственного Linux для R36SX V2.6.
Автор сообщает о физически проверенном ядре **5.12.4**, Buildroot rootfs и
TreeFrogUI; см. [инструкцию](https://github.com/ozkaoz/r36sx-hclinux/blob/main/docs/ONBOARDING.md).
На 1 октября 2026 проект архивирован.

Проверено локально: SHA256 наших `vmlinux.uImage`, `dtb.bin`, `avp.uImage`
**полностью совпадают** с тремя файлами из его
[GOLDEN_STOCK.sha256](https://github.com/ozkaoz/r36sx-hclinux/blob/main/manifests/GOLDEN_STOCK.sha256).
Это очень близкая программная база. Но документация того проекта описывает
256 МиБ RAM; наши исторические замеры указывают на меньший вариант, поэтому
готовый DTB и AVP оттуда нельзя считать подходящими без адаптации.

По [инвентаризации SDK](https://github.com/ozkaoz/r36sx-hclinux/blob/main/docs/SDK_AUDIT.md)
нужен **HCLinux SDK `hclinux-2024.02.y.2.tar.gz`**, примерно 2,1 ГБ, SHA256
`e3211b41f8d649c7d7838f7f19b8cca5cf30ba6cb1ff9545be6943845fbf8d5d`.
Сам архив в публичный репозиторий не включён. Имеющееся у нас дерево
`internet_sources/hcrtos` содержит RTOS, загрузчик и полезные определения
оборудования; оно не заменяет полный Linux BSP.

Собственное ядро в чужом проекте продолжает использовать заводской AVP.
Полная замена закрытого мультимедийного firmware и сборка своего Linux —
разные объёмы работы. Также в его
[состоянии на момент закрытия](https://github.com/ozkaoz/r36sx-hclinux/blob/main/CURRENT.md)
отдельно отмечен непроверенный физический запуск конечного сценария установки
на консоли с заводским NOR. Заявленные автором аппаратные результаты здесь
независимо не воспроизводились.

## Рекомендуемая последовательность

1. На штатном ядре сделать минимальную оболочку: меню, запуск программ,
   файловый менеджер, терминал с экранным вводом. Использовать существующие
   графику и кнопки; удерживать потребление памяти в пределах меньшего варианта.
2. Свежим замером подтвердить `uname -a`, `/proc/meminfo`, `/proc/cmdline` и
   `/proc/device-tree/memory/reg`, чтобы выбрать фактически загружаемый комплект.
3. Получить Linux BSP/SDK и воспроизвести ядро 4.4.186 под соответствующую карту
   памяти; сохранить штатные AVP, DTB и NOR на первом этапе. Load/entry нового
   uImage выводить из нового ELF, не копировать entry старого ядра вслепую.
4. Сделать минимальный свой rootfs и запуск оболочки из initramfs. Испытывать
   с отдельной SD-карты, сохраняя заводскую загрузку. Нужный файл ядра для
   меньшего варианта — вероятно, `advapi32.dll`, что сначала подтверждается
   замерами. Перепрошивка NOR ради переименования каталога для этого не нужна.
5. После рабочего базового ядра переносить нужные патчи 5.x из r36sx-hclinux,
   проверяя AVP RPC, структуры ioctl, экран, звук, кнопки, SD, USB и выключение.

Buildroot позволяет собирать rootfs отдельно от ядра и задавать свой overlay;
см. [официальное руководство](https://buildroot.org/downloads/manual/manual.html).
Это наиболее прямой путь к небольшой системе. Совместимость более нового
userspace со старым ядром и libc/toolchain надо проверять при сборке.

## Артефакты и пределы проверки

- Декомпиляция, инструкции и команды:
  `disasm/mips/r36sx-linux-boot/README.md` и соседние `.c`/`.s`.
- CRC, SHA256, DTB, версии ядер и содержимое initramfs:
  `disasm/linux/r36sx-stock-kernel/stock_inspection.json`.
- Извлечённые скрипты:
  `disasm/linux/r36sx-stock-kernel/initramfs_boot.txt` и
  `advapi32_initramfs_boot.txt`.
- Воспроизводящий анализатор:
  `disasm/linux/r36sx-stock-kernel/inspect_stock.py`.

Все четыре uImage прошли независимую проверку CRC32 заголовка и данных.
Ghidra успешно завершила анализ/экспорт. Точная `.config` ядра не извлечена:
маркера `IKCFG_ST` в распакованных ядрах нет. Сборки нового ядра, записи
на SD/NOR и аппаратного теста в этой задаче не было. Новые инструменты и
исполняемые пакеты не скачивались; образы читались как данные.
